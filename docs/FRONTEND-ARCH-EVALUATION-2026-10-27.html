Flowix 前端架构评审与评分

评审对象为 app/flowix-web/（React 19 + Tiptap + Zustand + Tauri IPC）。结论不基于文档自述，而基于依赖图全量扫描、门禁脚本实跑与代码抽样阅读；文档中与实际不符之处已单独标注。

一句话结论：这是一个「基建水准明显高于平均、模块边界明显弱于平均」的代码库。严格 TS（any 归零）、CAS 落盘、启动预算、6 万行测试说明团队有能力做硬工程；但 57% 的跨 feature 引用仍在穿私有路径、36 对循环依赖、agent 一个模块吃掉 30% 代码量，说明分层契约还停留在门禁文件里，没有变成日常写码习惯。

与仓库既有评审（72 分）的差异：口径不同。本报告把「错误处理机制」与「一致性/扩展性」单列并提高权重，且对「可维护性」按实测的 461 条 lint 抑制与 16 个千行文件从严计分，因此总分低 7 分，但问题清单基本互为印证。

01架构简洁性6.5 / 10

分三层：app（组合根）→ features/*（业务能力）→ lib/shared/platform（基础）。规则由 architecture.config.json 驱动，scripts/check-architecture.mjs 执行，存量记入基线。这套设计是成立的，问题全部出在「规则执行率」与「模块粒度」。

站得住的部分

  • 低层零反向依赖：lib/shared/platform 中对 @features/、@app/ 的引用为 0，分层方向没有倒灌。
  • 规则是配置驱动而非白名单：新增 feature 自动纳入约束；no-restricted-imports 从文件系统动态推导私有子路径，改名不会让规则静默失效。
  • Tauri 收口干净：327 处 invoke 中 317 处在 platform/tauri，平台外仅 10 处，这是很多 Tauri 项目做不到的。
  • 门面按能力拆分，没有 barrel：不存在 public/index.ts 一把梭，对启动体积友好——这与启动预算降到 324 KB gzip 是同一套工程判断。

问题

  • 边界合规率只有 42.7%。实测 806 条跨 feature 引用中，走 public/ 的 344 条，直连私有路径的 462 条。门面存在，但不是主要通道。
  • 存量违规被制度化冻结：architecture-baseline.json 记了 443 条私有引用 + 36 对双向依赖；eslint-suppressions.json 另有 409 条 no-restricted-imports。同一笔债记了两遍，且没有「每周必须还 N 条」的节奏。
  • 两条门禁当前都是红的：check:arch 报 3 条新增违规；eslint 实测 7 error / 201 warning，且 7 个 error 全部是跨 feature 私有导入，集中在 2 个文件——其中 surface/workspace-web-surface-renderer.tsx 一个文件占 5 条。「门禁存在」不等于「门禁守住了」。
  • 违规不是历史遗留，而是正在产生：workspace-web-surface-renderer.tsx 是 surface 渲染的协调入口，属于较新的代码。它一次穿墙 5 处，说明边界规则在「写新代码时」没有被内化，只在「提交时」被检查。
  • 模块粒度失衡：agent 69,680 行（占前端 30%）、agent/thread-card 单目录 34,817 行、agent/store 20,616 行。一个 feature 内部再长出 14 个子目录、5 层深度，本质上已经不是「一个模块」。
  • 组合根渗业务：app/main-window-effects.tsx 里承载 memo 事件 → 缓存失效 → todo 计数刷新等业务链，另有 24 条 composition-private 基线。app 名义上是装配层，实际是第五个业务模块。
  • foundation 有漏点：lib/store/settings-store.ts 让「基础层」持有应用状态，lib/types/agent-workspace.ts 是 agent 领域 DTO 下沉到了 lib。
判断：分层骨架是这几年少见的好设计，但「合规率 42.7%」意味着它现在主要起记录作用，而不是约束作用。继续按这个速度加功能，基线会从「债」变成「宪法」。

02代码健壮性7.5 / 10

这一维是全场最强项。类型纪律、持久化并发、乐观更新回滚都有真实设计，不是「写了 try/catch」式的健壮。

站得住的部分

  • 类型纪律接近满分：any 实测 0 处、@ts-ignore 0 处、非空断言仅 6 处；strict + noUnusedLocals + noFallthroughCasesInSwitch 全开，no-explicit-any 设为 error。这在 17 万行规模里非常罕见。
  • 保存链路是真防护：document-commit-queue.ts 每文档单写者 + latest-value 槽；save-queue.ts 用 CAS（expectedContent + revision）拒绝丢失更新，写后再排最新内容，并配恢复草稿。并发冲突是「有解」而不是「靠运气」。
  • agent 提交有回滚语义：composer-submission-controller.ts 乐观更新失败后恢复草稿，并区分「已受理 / 被拒」；启动与聚焦后做对账补偿（use-agent-events.ts）。
  • 有超时意识：历史读取 30s 超时；单条消息渲染有降级路径，坏数据不会拖垮整个会话列表。
  • 三态覆盖到位的地方做得完整：document-container.tsx 有 loading/empty/error + 重试；document-save-status.tsx 有冲突三选一；CSV 预览三态齐全。

问题

  • Tiptap 是最大的裸奔区：markdown-editor.tsx:651 用 new Editor(...) 命令式创建，没有 try/catch，也没有编辑器级错误态。ProseMirror 的 NodeView / dispatch 异常发生在 React 之外，结果是「编辑区空白 + 无任何提示」。
  • 索引访问不安全：noUncheckedIndexedAccess 未开，arr[i] 仍被推断为 T 而非 T | undefined；as unknown as 有 118 处（生产 47 处，集中在 frontmatter-model.ts）。
  • 异步失败无人接：729 处 void promise，仅 15% 同行接了 .catch；剩下的既没有全局 rejection 兜底，也没有统一上报（详见第 4 节）。
  • save-barrier.ts 无超时：单 pending + flush 轮询，一旦某次保存悬挂，flush 会永久等待；且只覆盖 3 处，主编辑器不在其中（主编辑器靠 commit-queue 兜，属于设计分工，但边界没写清）。
  • 错误对象不成型：359 处 throw new Error，自定义错误类只有 6 个。很多「该重试 / 该提示 / 该忽略」的判断只能靠字符串匹配。

03可维护性6.5 / 10

日常改动体验是好的：文件小、命名统一、测试就在旁边。真正拉低分数的是「少数巨型文件 + 被合法化的 lint 债务 + 门槛全红」这个组合——lint 7 error、架构检查 3 条新增、单测 31 个失败，三条防线同时失效。

站得住的部分

  • 文件规模分布健康：57% 的文件 <100 行，平均 158 行；<300 行占 87%。这说明作者有拆文件的习惯。
  • 命名有纪律：32 个 store 全部导出为 use*Store，没有混入 Provider 模式；action 命名虽不统一（set/load/open/flush 混用），但整体可读。
  • 测试文化是真实的：405 个测试文件、3,036 个用例、62,168 行，测试∶生产 = 0.37∶1；save-queue、buffer-registry、agent-session-actions（3,153 行）等核心链路都有测。3005 个用例是通过的，说明主体健康，问题在最后一公里没有维护。
  • i18n 骨架完整：en-US / zh-CN 各 2,263 个 key，差集为 0。

问题

  • 16 个文件超过 1,000 行，最大的 table-document-view.tsx 3,352 行（同时 24 条 lint 抑制、0 个测试）；external-agent-settings-controller.ts 2,457 行、preferences/sections/agent.tsx 2,085 行、agent-thread-card-view.tsx 2,076 行。复杂度最高的三个正好也是没测试的三个。
  • lint 债务 461 条 / 198 文件，其中 409 条是边界违规（见第 1 节）。抑制文件把架构问题伪装成 lint 噪音，新人读代码时看到的是「这里被允许了」而不是「这里欠着」。
  • 没有覆盖率闸门，且当前测试是红的：vitest.config.ts 全文无 coverage 段；实跑 vitest run 结果为 13 个文件 / 31 个用例失败（405 文件 / 3,036 用例 / 114 秒）。失败集中在 stable-caret.ts 与 jsdom 环境（resizeObserver?.unobserve is not a function），属环境兼容问题而非产品缺陷，但它让「测试作为回归闸门」整体失效——红着的测试等于没有测试。
  • 注释中英混杂：9,427 行注释里中文 3,197 行，且常有同文件混用；另有 882 行硬编码中文字符串没走 i18n（i18n 处于「半迁移」状态）。
  • 文档和代码脱节：CLAUDE.md 写的目录树是 main.tsx / components/editor/，实际是 entrypoints/desktop.tsx / features/editor/；文中 lib/tauri/client.ts 这个路径不存在。全文 0 次提及 ESLint 与模块边界规则，而这两条已经挂在 pre-commit 上。
  • 死代码：shared/ui 30 个组件里 2 个全仓 0 引用（surface-suspense-host.tsx、textarea.tsx），生产依赖里 5 个零引用包。

04错误处理机制6.0 / 10

链路是「捕获 → 转换 → 呈现 → 记录」四段。这个项目前两段有设计、第三段不统一、第四段基本缺失。

站得住的部分

  • 错误边界实现质量高：shared/error-boundary.tsx 有 getDerivedStateFromError、componentDidCatch 走 logger、resetKeys 变化自动重置并强制重挂载、手动重试按钮。SurfaceBoundary 还有测试。
  • 边界下沉到了面板级：主列表、工作区、浏览列、状态栏、每个 surface 各一个边界——单个 surface 崩不会带走整页。这是正确方向。
  • 文案映射有兜底：friendly-error-message.ts 按 timeout / 429 / 网络 / 鉴权归一，最终回退调用方的 fallback key，不会出现空文案。
  • 保存错误有专门 UI：保存状态条 + 冲突三选一，属于「错误即交互」的正确做法。

问题

  • 没有全局兜底：全仓 window.onerror / unhandledrejection 命中数为 0。promise 被 reject 后既没有 toast、没有崩溃页、也没有日志汇总——线上出问题等于黑盒。
  • 边界只有 9 处，且没有单卡片粒度：ErrorBoundary 3 处、SurfaceBoundary 4 处、局部 2 处。memo 列表整列共用一个边界，一条坏数据可以让整列消失。
  • 日志不落地：lib/logger.ts 只有 4 个级别 + console，debug 仅 DEV；没有脱敏、不写文件、不上报。注释要求「不要记录路径」，但 save-queue.ts 直接记了 ctx.path。
  • 文案出口不唯一：toast.error 399 处，friendlyErrorMessage 只有 106 处。也就是说大部分错误把后端原始 message 直接怼给用户。另有 platform/tauri/errors.ts 第三套域内映射。
  • 静默吞错 12%：436 个 catch 块里 15 个空、51 个只 console；.catch 里静默 54 处。多数是清理/降级场景，风险低，但完全不可观测。
  • 关键交互缺恢复路径：agent 发送失败只「toast + 恢复草稿」，没有「重发」按钮；流中断只置 reconnect notice，无自动续传。
  • 上报钩子是死的：ErrorBoundary 提供 onError 回调，但 app.tsx 两处调用都没传。
最该修的一条：挂上 unhandledrejection + window.onerror，并给 ErrorBoundary 接 onError。这两件事加起来不到 40 行代码，却能把「729 处 void promise 中 85% 无人接」的暴露面从「整站黑盒」降到「可观测」——性价比是所有建议里最高的。

05整体一致性与扩展性5.5 / 10

同一个问题在不同 feature 里有不同答案。这在 20 个模块、多个作者、两年演进的规模下几乎必然发生，但这里缺的是「收敛动作」，而不是「收敛意识」——设计 token、surface 注册表、public API 都做了，就是没推广开。

站得住的部分

  • 设计 token 有真源：styles/theme/*.css 5 套主题 × 54 个变量，tailwind.config.js 映射了约 20 个语义色。基础设施是在的。
  • surface 是真注册表：19 种 kind 集中注册，satisfies Record 能在编译期兜住「注册了但没实现」。
  • IPC 有统一客户端：299 个文件走 @platform/tauri/client，不各写各的 fetch 封装。
  • plugin 是声明式、受限执行：manifest v2 + 6 个 renderer id，未知 format 在安装前拒绝。作为「产物插件」模型是成熟的。
  • 启动体积有预算并被执行：324 KB gzip / 340 KB 预算，靠 manifest 复算静态闭包而不是靠肉眼。这条其实属于工程基建的亮点。

问题

  • store 是「形式统一、写法分裂」：32 个 zustand store 存在三种范式——note-store.ts（930 行，内联 repository + 直接引用 3 个别的 store）、agent-session-store.ts（647 行，persist + subscribeWithSelector + 7 个 slice）、document-store.ts（257 行薄壳，委托 service）。devtools 使用数为 0。
  • 跨模块通信有四套并存：直接 getState()（1,761 处）、lib/event-dispatcher、lib/memo-dispatcher、Tauri event-bus（29 处 / 75 个订阅）。哪种场景该用哪套，没有规则。
  • 设计 token 被大面积绕过：arbitrary value 3,849 处，其中 text-[var(--foreground)] 455 处、text-[var(--muted-foreground)] 634 处——而映射好的 text-foreground 只用了 8 次。token 建好了，但没人用语义类。
  • CSS 无预算：42 个文件 / 17,429 行 / 391 个 !important。JS 有 340 KB 闸门，CSS 没有对应约束。
  • 同一件事多种实现：文件树 2 套（notebook-file-tree 1,671 行 vs folder-file-tree 658 行）、拖拽排序 3 套、通知 4 套（sonner / actionable-notice-store / created-document-notices / SurfaceNotice）、loading skeleton 6 份。
  • 扩展成本高：新增一种文件 surface 要改约 11 个文件 + 9 处 switch（surface-registry.ts、surface-contract.ts、renderer-registry、resolvers…）。有注册表，但没有单点注册。
  • plugin 不能扩展 UI：只能产出既有 renderer 的产物，无法新增 surface 或注册组件——作为「插件平台」是封闭的。
  • 概念长期撕裂：Note 6,741 次 / Document 3,881 次 / File 2,686 次 / Memo 1,448 次；note-store 与 document-store 并存。features/document 里提到 note 266 次，features/memo 里提到 document 316 次。

06三个跨维度的系统性问题

上面五节的问题，本质上收敛为三件事。改这三件，五个维度的分数会一起动。

1
「规则」和「习惯」之间没有桥

门禁、基线、抑制文件都做了，但三者把同一笔债记了三遍，且没有递减机制。结果是：规则全绿时，债务仍在增长。缺的不是工具，是清偿节奏。

2
缺少 domain 层，业务模型散在 feature 里

note/document/workspace 是被 8 个 feature 共享的核心概念，却各自持有 store 与类型。这会同时制造：462 条私有引用、36 对环、Note/Document 命名撕裂、以及 4 套通知。一个 domain 层能同时解掉这四个症状。

3
复杂度向三个文件集中

3,352 / 2,457 / 2,085 行的三个文件，同时是「最大文件 + lint 抑制最多 + 无测试」三重交集。它们不是历史遗留，而是当前仍在生长的热点（table / agent settings / agent thread card）。

4
错误链路断在「记录」和「恢复」

捕获有、提示有、转换半有、记录几乎没有、恢复基本没有。用户看到的是「toast 一闪 + 原始英文报错」，开发者看到的是「控制台，然后什么也没留下」。

07改进建议（按投入产出排序）

原则：先做「小改动、大杠杆」，再做「结构改动」。每条都给了可验收的指标，避免又变成一份写完就归档的文档。

P0 · 本周

1. 补全局错误兜底，把黑洞变成可观测

entrypoints/desktop.tsx 注册 window.onerror + unhandledrejection；app.tsx 两处 ErrorBoundary 传入 onError；logger 增加一个 sink（先写 console + 内存环形缓冲，后续接文件/上报）。

验收：故意抛一个未捕获 promise rejection，能在日志里看到结构化记录，且用户侧有降级提示。改动量 < 80 行。

P0 · 本周

2. 修绿当前两条红灯，并给基线加「只减」机制

先修 3 条架构违规 + 7 条 lint error（两者其实是同一批穿墙引用，共 2 个文件）。然后让 check-architecture.mjs 输出「剩余债务数 + 较上次的变化」，CI 对「债务数上升」直接失败（现在只对新增违规失败）。

验收：npm run lint 与 check:arch 同时为绿；443 → 不超过 443，且每次 PR 能看见这个数字。目标：3 个月内降到 300 以下。

P0 · 本周

3. 给三个巨型文件上「禁止增长」闸门

先不拆（拆要排期），但加一条脚本：table-document-view.tsx ≤ 3,352、external-agent-settings-controller.ts ≤ 2,457、agent-thread-card-view.tsx ≤ 2,076，超一行就失败。同时给它们各补 3 个行为测试（先锁住现有行为，再谈拆分）。

验收：三个文件行数曲线由升转平；三个月内各降 40%。

P1 · 1–2 月

4. 建 domain/ 层，收敛 note / document / workspace

把被 >3 个 feature 共享的实体、类型、纯函数（不含 React、不含 store）下沉到 domain/；先搬 note-store 与 document-store 共用的模型，再让 feature 通过 domain 读取，而不是互相 import store。这是唯一能同时消解 462 条私有引用、36 对环、Note/Document 内耗的杠杆点。

验收：私有跨 feature 引用 462 → <250；cycles 36 → <20；note-store 被外部 feature 引用从 39 处降到个位数。

P1 · 1–2 月

5. 统一错误呈现：一个出口、一个映射

抽 presentError(err, { fallbackKey })，内部完成：错误归一 → 分类映射 → toast/内联二选一 → 日志。禁止组件里直接 toast.error(err.message)；用 lint 规则限制 toast.error 的直接调用点。合并 error-message / friendly-error-message / platform/tauri/errors 三套映射。
